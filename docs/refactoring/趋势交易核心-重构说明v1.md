# 2. 核心问题与优先级

## 2.1 P0：正确性、审计一致性、可靠性

| 问题 | 原风险 | 本轮处理 |
|---|---|---|
| 重复审批不幂等 | 第二次审批可能先切 current，后写审核记录失败，形成 current/Review/Manifest 分叉 | 审批专用锁 + 参数完全一致幂等 + 参数不一致 fail closed |
| 审批先激活再补审计产物 | 中途失败产生“正式版本已生效但审计链不完整” | 全部不可变产物先生成和复核，最后 CAS 激活 |
| Approval Manifest 沿用旧 `file_hashes` | 无法验证批准后的 Parquet、报告和审核记录 | 重建完整路径/哈希链，覆盖审批输入与输出 |
| Coverage 缺报告返回空缺口 | “无法验证”被误报为“无缺口” | 独立血缘校验，报告缺失/错版/行数错配均抛错 |
| 双 Catalog 自动猜测 | 可能选择空或过期数据库 | `catalog_backend.json` 明确后端；无标记双库冲突报错 |
| Pointer 与 Catalog 非整体事务 | 任一步失败可能形成 A/B 两个 current | 品种级锁 + 激活日志 + 回滚 + 启动恢复 + 一致性后验 |
| 首次发布缺 CAS | 两个首次发布任务都可能认为 current 为空 | 支持 `expected_current=None` 的显式 compare-and-swap |
| 锁超龄误抢/误删 | 长任务锁可能被抢；旧 owner 可能删除新锁 | PID 存活检测、文件状态校验、token 所有权释放 |

# 3. V1 交付中的重构架构（历史快照）

## 3.1 新增核心组件

### `historical_data.integrity`

统一实现：

- `json_bytes()`：与不可变 JSON 落盘编码完全一致；
- `canonical_json_bytes()` / `stable_hash()`：内容寻址；
- `sha256_file()`：流式文件哈希；
- `frame_hash()`：包含列、dtype、行序的语义哈希；
- `strategy_frame_hash()`：保持既有 dataset version 算法兼容。

### `historical_data.locking`

无第三方依赖的跨进程文件锁：

```text
O_EXCL 创建
→ 写 PID / timestamp / token
→ fsync
→ 存活进程不抢锁
→ 未知 owner 在 stale 窗口内不删除
→ release 必须匹配 token
```

### `historical_data.lineage`

策略可见 current 的独立验证器：

```text
Pointer
→ Dataset Manifest
→ Curated path/hash
→ Quality Report path/hash/version/rows
→ Bars dataset_version
→ Pointer/Catalog current
```

任一环节缺失或不一致即 `DataLineageError`。

### `historical_data.review`

审批协调器将事务拆成明确阶段：

```text
load candidate
→ validate/reuse immutable approval plan
→ prepare approved bars/report/manifests
→ write catalog dataset + immutable review
→ verify all artifacts
→ CAS activate current
```

## 3.2 关键修改的 Before / Problem / After

| 事项 | Before | Problem | After | Benefit | Compatibility |
|---|---|---|---|---|---|
| 审批入口 | API 内完成所有步骤 | 函数过大、失败边界不清 | API 委托 `ReviewApprovalCoordinator` | 规则可单测、重试路径明确 | `approve_review()` 调用方式保留 |
| 重复审批 | 每次生成新版本并先切 current | 审计分叉 | 完全相同请求返回原版本；不一致请求拒绝 | 幂等、不可变 | 增加 `actor/decision` 可选参数 |
| Approval Manifest | 复制旧 Manifest 再改路径 | 哈希不对应新制品 | 对全部输入/输出重新计算 SHA-256 | 可验证批准版本和审批来源 | Manifest schema 增量扩展 |
| Coverage | 报告不存在时 `{}` | 空列表误导业务 | `load_current_lineage()` fail closed | 不再把未知当正常 | 正常数据返回结构保持 |
| Catalog 选择 | DuckDB 文件优先 | 双库场景猜错 | 后端标记权威；冲突直接报错 | 可重复、可诊断 | 单一旧库自动迁移标记 |
| current 更新 | Pointer 后 Catalog | 部分失败不一致 | 锁 + journal + 回滚 + 恢复 + CAS | 崩溃可恢复 | Pointer 路径格式保留 |
| 不可变 Parquet | 文件存在即返回或覆盖风险 | 无法判断冲突重试 | 语义哈希一致才幂等；不同则报错 | 防止静默篡改 | 对同内容重试兼容 |
| 可选集成 | 包导入时加载全部 SDK | 核心导入失败 | `__getattr__` 惰性加载 | 减少非必要运行依赖 | 导出名称保持 |

# 7. 性能优化与复杂度

## 7.1 本轮可靠性路径

审核与 current 发布的重点是正确性，不是吞吐量。本轮新增锁、哈希和事务日志会增加少量必要 I/O；没有发布前后真实生产数据基线，因此：

> **不能证明本轮 Review/Storage 事务重构提高了性能。**

可以确认的性能相关改进：

- 语义相同的不可变制品重试直接复用，不重复覆盖；
- 审批中断后复用 `approval_plan` 和已写制品，不重新生成平行版本；
- 哈希文件按 1 MiB 分块读取，避免一次性加载大文件；
- 锁仅包围发布边界，没有将下载和全部计算串行化。

## 7.2 策略热路径基准

重新执行 `scripts/benchmark_refactor.py`：Python 3.13.5、720 根 D1、每项预热 1 次后测量 7 次中位数，无磁盘和网络 I/O。该脚本比较的是代码库既有“旧实现函数 vs 当前共享实现”，用于确认重构后的热路径行为和结果等价；**不应把以下加速归因于本轮审核事务修改**。

| 场景 | Before 中位耗时 | After 中位耗时 | 加速 | Before 峰值 | After 峰值 | 内存变化 |
|---|---:|---:|---:|---:|---:|---:|
| 共享特征准备 | 41.190 ms | 19.895 ms | 2.070× | 224.3 KiB | 280.7 KiB | **+25.12%** |
| Detector replay | 500.063 ms | 373.990 ms | 1.337× | 810.0 KiB | 604.0 KiB | **-25.43%** |
| 多资产 timeline | 96.739 ms | 48.538 ms | 1.993× | 892.0 KiB | 564.2 KiB | **-36.75%** |

结论：三个路径耗时均下降；共享特征准备以额外峰值内存换取复用和速度，不能笼统声称“所有内存都改善”。原始 JSON：`性能基准v1.json`。

# 12. 向后兼容性

## 保持兼容

- `HistoricalDataService`、`load_bars()`、`market-data` 主入口保留；
- `approve_review(run_id, reason)` 旧调用仍可运行，新增参数均有默认值；
- SQLite/DuckDB 旧单一 Catalog 可自动识别并生成后端标记；
- Manifest/Pointer 中旧绝对路径与工程相对路径仍可解析；
- Dataset version 的既有策略哈希算法保留；
- OKX/MT5 的公开导出名称保持。

## 行为收紧（有意的 fail-closed）

- 同时存在两个 Catalog 且无标记时不再自动选择；
- Coverage 缺质量报告或血缘不一致时不再返回空缺口；
- 已批准记录的原因/actor/decision 不一致时不再允许再次审批；
- 已拒绝候选不允许直接 approve；
- 同一路径不可变 Parquet 内容不同不再覆盖；
- 并发发布 current 变化时 CAS 失败，需要重新读取后重试。

这些属于正确性修复，不提供旧危险行为的兼容开关。
