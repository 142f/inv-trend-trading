# 项目系统重构与前后端模块划分方案 v1

## 0. 文档信息

| 项 | 内容 |
|---|---|
| 审计对象 | `src/inv_trend/`（274 个 .py）、`scripts/`（24 个）、`tests/`（105 个）、`deliverables/`（6 个产物）、`artifacts/`、`docs/` |
| 代码基线 | 工作区 23 项变更，其中 `scripts/美股前100指标.py`、`tests/test_美股前100指标.py`、`src/inv_trend/application/多品种验收.py` 未跟踪；`deliverables/` 被 `.gitignore` 排除 |
| 审计方式 | 逐模块静态阅读、路由/CLI 参数提取、页面交互脚本读取、文档（流水线规范、监控架构、模块依赖契约）交叉核对 |
| 本文性质 | 重构方案与审计结论；本轮只读，不改代码 |
| 结论 | 业务模型完整，**但当前不是前后端分离系统**：全仓库只有 1 个 HTTP 服务（监控看板 4 条路由），其余页面为离线静态 HTML（F3–F6）与手工文档（F7） |

一句话结论：

> 项目已经把「数据 → 指标 → 策略 → 监控 → 通知 → 回测 → 研究 → 存储」这条业务链做全了，但页面层只覆盖「看」，不覆盖「操作、回放、投递重试」；同时存在「模型有但模块无」「页面有但接口无」「接口有但页面无」三类错位。重构的核心不是造 SPA，而是**先定模块边界与统一读模型，再让页面与接口一一对齐**。

页面事实更正：全仓库共 6 处 HTML 出口，只有 F1/F2 由 HTTP 服务实时渲染，其余 4 处（F3–F6）是离线生成的静态文件，F7 是手工文档。因此下文「前后端」一律指「渲染层（页面）／服务层（Python 服务 + 唯一 HTTP 网关）」，不代表存在两套独立部署。

## 1. 重构总体方案

### 1.1 现状判定

| 判定项 | 事实 | 证据 |
|---|---|---|
| 是否有前端工程 | 无。没有 `package.json`、vite/webpack、组件目录 | `**/package.json` 仅命中 `.venv` 内 Playwright 驱动 |
| 是否有 Web 服务 | 仅 1 处：监控看板 FastAPI | `monitoring/看板.py` L194-L254；`cli/监控运行.py` L125-L135 `uvicorn.run(app, host='127.0.0.1', port=args.port)` |
| 页面如何产生 | 4 类由 Python 渲染成单文件 HTML，1 类由脚本内嵌 JSON 生成，1 类为手工文档 | 见 §2.1 |
| 前后端通信 | 仅监控看板有 HTTP JSON；其余页面数据全部内嵌，无运行时请求 | `reportData` script 标签、`payload` 内嵌对象 |
| 数据入口 | 统一为 `HistoricalDataService` → `MarketDataPipeline`（acquire→transform→persist，read 独立） | `docs/数据管理流水线规范_v1.md` §1；`data/api.py` L31-L76 |

结论：现有「后端」是**服务层 + CLI**，不是 HTTP API 层；现有「前端」是**报表产物**，不是应用。因此重构目标应定义为：

> 保留批处理与静态报表的既有价值（研究可复现、离线可审计），在其上补一层**统一只读 API + 报表注册表**，并把页面按业务模块收敛到同一套 DTO，避免每加一个页面就复制一套取数/口径逻辑。

### 1.2 目标架构（4 层）

```text
┌─────────────────────────────────────────────────────────────┐
│ L4 展示层  PageModule: monitor / backtest / daily / research │
│            snapshot-top100 / audit-report                    │
├─────────────────────────────────────────────────────────────┤
│ L3 网关层  FastAPI Gateway（唯一 HTTP 出口，默认 127.0.0.1）  │
│            /api/* 只读 JSON   /r/* HTML 投影                  │
├─────────────────────────────────────────────────────────────┤
│ L2 领域服务  Data / Feature / Strategy / Monitor / Replay /   │
│            Notify / Research / Backtest / Report / Portfolio  │
├─────────────────────────────────────────────────────────────┤
│ L1 基础设施  Repository(v3) / EventStore / Research DB /      │
│            DataLake / OKX 适配器 / 进程监督                    │
└─────────────────────────────────────────────────────────────┘
```

四条硬约束（重构必须固化，写进测试）：

1. **单一数据入口**：任何页面/脚本取行情只能走 `HistoricalDataService.load_bars / load_bars_version`，不得自行读 CSV/Parquet 或自行复权。
2. **单一指标入口**：任何指标只能走 `FeatureRequest` + `PreparedBars`，不得在页面或脚本内重写 EMA/SMA。
3. **单一读模型**：页面只消费 DTO（`MonitorOverview`、`BacktestReport`、`DailySnapshot`、`StudyReview`、`SnapshotTop100`），DTO 由服务层产出，渲染层不做计算。
4. **单一写边界**：页面不写库。所有状态改变只经 CLI/服务，且必须留回执。

### 1.3 与现状的差异（重构要解决的 4 件事）

| # | 现状 | 重构后 |
|---|---|---|
| 1 | 5 类页面各自定义数据结构与渲染 | 统一 `ReportKind` 注册表：`monitor` / `backtest` / `daily` / `study` / `snapshot` |
| 2 | 监控看板无筛选、无刷新、无操作入口 | 看板补筛选/排序/刷新；运维操作走受控 POST + 本地令牌 |
| 3 | 回放只能在 CLI 跑，无进度、无结果页 | 新增 Replay 模块 + `/r/replay/{id}` 结果页与进度字段 |
| 4 | 通知投递只有汇总计数，无 attempts 明细 | 新增投递明细接口与页面时间线 |

### 5.5 EMA 均线

本仓库 **EMA 确实存在**，但有两套用途，公式一致（`ewm(span=n, adjust=False)`），周期与门槛不同：

| 用途 | 周期 | 实现 | 预热门槛 | 出现页面 |
|---|---|---|---|---|
| 指标快照 | 10 / 20 / 55 / 144 / 169 | `core/features.py` `ema_periods` | 169 根（EMA169 最长） | F6（10/20/55 画线，144/169 仅表内） |
| 趋势关系（三对） | 10 / 20 / 55 → 对 (10,20)(10,55)(20,55) | `core/EMA趋势策略.py` `PAIRS` | 60 根 | **无页面**（F6 的「多/空/混」是同一口径的重算） |
| MACD 快线/慢线 | 12 / 26 + DEA 9 | `features.py` `macd_periods`、`EMA趋势策略.signals` | 169 / 60 | F6 详情 DIF/DEA；F4 日报 MACD SVG |
| 海龟系统 | **不使用 EMA** | `adapters/multi_asset/strategy/indicators.py`（通道/ADX/ATR） | 无 | F1/F2/F3/F5 均无 EMA |

口径差异（需在页面写明）：

1. F6 的「三对 EMA 多头/空头」用的是 `ema_10/20/55` 快慢关系，与 `EMA趋势策略.PAIRS` 完全一致；但 **F6 的 144/169 不参与方向判定**，只作展示。
2. `EMA趋势策略.signals` 要求 ≥60 根，`features.py` 要求 169 根；同一只股票在两个模块里「是否可用」结论可能不同（HONA 93 根：策略可用、看板标 `warmup<169`）。
3. 海龟链路的趋势过滤用 ADX/通道，不用 EMA；F1/F2/F3 页面上出现「趋势（UP/DOWN）」时，指的是海龟方向，不是 EMA。
