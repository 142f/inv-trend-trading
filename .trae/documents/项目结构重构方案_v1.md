# 项目结构重构方案（契约驱动解耦）v1

> 目标：在**对外接口行为与运行结果完全不变**（数值基线一致）的前提下，按 `tests/test_architecture_boundaries.py` 已确立的分层契约，逐条消除反向依赖与循环依赖，形成依赖单向、职责单一、可扩展的结构。
> 范围决策（已与用户确认）：**契约驱动解耦**；兼容转发层与 `_v1/_v3` 并存模块**全部保留**，只修正依赖方向，不改模块名、不改目录层级、不破坏任何现有导入路径。

---

## 1. 摘要

本方案不重排目录、不改模块名，而是做三件事：

1. **把被下层需要的接口定义下移**（新增纯协议包 `inv_trend/ports/`，并把纯 DTO `DailyArtifactPublication` 下移），使 `adapters` 不再需要 import `application`。
2. **把放错层的代码搬回正确层**（`storage` 中的上层发布函数、`core` 中的文件写入函数、`data` 需要的 v3 目录原语），消除 `storage→application/adapters`、`core→storage`、`data→storage`。
3. **把契约固化进测试**（新增「包级依赖无环 + 反向边为空」的自动测试），使结构不再回退。

产出：目录结构说明 + 模块依赖图 + 关键接口变更清单 + 验证结果（第 7 节）。

### 2.4 已核实的关键事实（决定机制）

1. `storage/制品.py` 的 `backtest_publish`（L12）与 `daily_publish`（L97）**全仓库零调用**（`src`、`tests`、`scripts`、`research` 均为零命中）。同模块的 `read_backtest` / `read_daily` 有调用者（`application/backtest/artifacts.py:173`、`application/daily/workflow.py:162`），且是纯读取，不触上层。
2. `core/滚动协议.py` 的 `immutable_json` 唯一调用方是 `application/滚动验证.py`（13 处，L130–L289）。
3. `application/daily/ports.py` 的协议被适配器**仅用于类型标注/继承声明**；`adapters/daily/composition.py:19` 与 `observability/report_renderer.py:14` 均为 `TYPE_CHECKING` 注解。
4. `ArtifactPublisherPort.publish` 的返回类型 `DailyArtifactPublication`（`application/daily/artifact_publication.py:21-28`）是**纯 frozen dataclass**（`Path` + `Mapping`），`ArtifactPublicationService` 依赖 `isinstance` 校验，因此下移时必须保持**同一个类对象**（由原路径 re-export）。
5. `observability/report_model.py`（仅 re-export `application.daily_models`）与 `observability/backtest_html.py`（转发 `application.backtest.legacy_report`）**全仓库零外部引用**（除 `observability/__init__.py` 的懒加载分支）。
6. 测试对内部模块路径的耦合很小：全仓库仅 5 个测试文件出现 `inv_trend.` 字面导入（21 处），移动模块的风险面可控。
7. 当前基线：全量回归 **6 failed / 1425 passed / 7 warnings**（6 项失败全部是既有未提交改动导致的监控回放录制 fixture 不匹配，与本轮无关）。

## 3. 目标架构与不变式

### 3.1 目标分层（依赖只允许从上层指向下层）

```
L0  domain, config
L1  core
L2  ports            ← 新增（纯协议 + 纯 DTO）
L3  data
L4  storage
L5  observability    ← 纯渲染层，位于 data/storage 之上、application/adapters 之下
L6  application
L7  adapters, integrations
L8  notifications
L9  monitoring
L10 cli              ← 组合根
```

> 说明：`adapters/daily/composition.py` 是「文件系统写入适配器 + 渲染适配器」的**组装点**，本质是组合根职责，但它位于 `adapters` 且被 `application` 调用，历史上形成双向边。本方案保持现有测试禁令，不把它提升为 `cli`（避免改动 `DailyMarketScanService` 公开构造签名），而是通过 §4.2 的方式消除 `adapters → observability`。

### 3.2 要固化的不变式（写成测试）

- **I1 无环**：包级依赖图中不存在双向边（即不存在长度 ≥2 的环）。
- **I2 反向边为空**：`adapters` 不再依赖 `application`（8 条过渡白名单收敛为 0 条）。
- **I3 新增禁令**：`storage` ✗ → `application`/`adapters`；`core` ✗ → `storage`；`data` ✗ → `storage`；`observability` ✗ → `application`。
- **I4 既有禁令不变**：core/domain/application/observability/data 的既有禁令逐字保留。
- **I5 残余边显式化**：§2.3 的边登记为一个具名常量集合，测试断言「观测集合 == 该常量」。

## 6. 验证方案

### 6.1 每阶段必跑

1. `python -m pytest -q --basetemp .tmp/pytest-<phase>` → 必须 **6 failed / 1425 passed / 7 warnings**（与基线逐项同名同错；失败项为既有监控回放 fixture 不匹配）。
2. `python -m pytest -q tests/test_golden_master.py` → 事件/订单精确、浮点 1e-10 容差通过。
3. `python -m ruff check src scripts research tests --select F` → All checks passed。
4. 该阶段的专项合同测试（见各 Phase 的「验证」条）。
5. 数值/接口 A/B digest：对本阶段搬动涉及的入口，比较「搬家前 / 搬家后」的输出摘要 sha256（沿用 `结构优化验收_20261019` 的 digest A/B 方法）。

### 6.2 结构性验证

- 新增/收敛的依赖测试（§3.2 I1–I5），每阶段后白名单与循环计数必须单调递减并最终归零。
- `python scripts/遗留模块引用审计.py`（Phase 3 删除前置条件）。

### 6.3 review3 次（沿用仓库既有约定，见 `docs/结构重构验收_20261006.json` 的 `review.passes: 3`）

每个阶段在**提交前**做 3 次独立复核，结果写进该阶段回执：

1. **第 1 次 — 等价性复核**：逐行 diff 对照，确认搬动只改 import 位置、不改表达式；对涉及数值的搬动做 digest A/B。
2. **第 2 次 — 接口与调用方复核**：全仓库检索被搬动符号的所有引用（含 `TYPE_CHECKING`、字符串注解、`getattr`/`import_module` 动态导入、测试与脚本），确认 shim 覆盖完整、`isinstance` 仍是同一类对象。
3. **第 3 次 — 反向/对抗复核**：专门找「搬动后新增的反向边或循环」与「被 shim 掩盖的旧路径失效」，并用依赖图重新计算 I1/I2/I5 是否满足；同时跑全量回归。

整体方案在 Phase 6 再走一遍同样的 3 次复核，形成整体回执。

## 8. 假设与决策（执行者不需要再选择）

| # | 决策 | 理由 |
|---|---|---|
| D1 | 新增顶层包 `inv_trend/ports/`（additive），不移动既有模块名/目录 | 协议需要位于 `application` 之下供 `adapters` 引用；既有导入路径全部由 shim 保留 |
| D2 | `ports` 只允许依赖 `inv_trend.core`（`SignalEvent` 等） | 保持 `domain` 的「零内部依赖」与「禁 pandas/numpy」契约不被破坏 |
| D3 | `adapters → observability`（E2）**保留现有禁令**，通过注入默认渲染器消除，而非把该方向合法化 | 遵循既有测试契约的原始意图（该白名单是「transition」），避免削弱守卫 |
| D4 | `observability` 定位为纯渲染层，位于 `data/storage` 之上、`application/adapters` 之下 | 与既有两项禁令（observability ✗ data/adapters）自洽 |
| D5 | 零引用废弃转发模块（`observability/report_model.py`、`observability/backtest_html.py`）在审计确认零引用后删除，独立提交 | 它们的存在本身就要求 observability 依赖 application，与 I3 不相容；删除是唯一既满足契约又「改动最小」的做法（`_v1/_v3` 与文档化兼容模块仍全部保留） |
| D6 | `storage/结构化存储_v3.py`、`storage/数据迁移_v3.py` 下移到 `data/`，`storage/` 保留同名 shim | 整模块下移比抽取子集风险更低；`storage → data` 单向关系保留 |
| D7 | 本轮不动 `monitoring`/`notifications`/`integrations` 的跨层边，改为显式登记的残余契约 | 超出用户批准范围；先保证不劣化 |
| D8 | 每阶段独立提交（含回执），不合并为一个大提交 | 满足「分阶段、可验证推进」与可回滚 |

## 9. 风险与回滚

| 风险 | 等级 | 缓解 |
