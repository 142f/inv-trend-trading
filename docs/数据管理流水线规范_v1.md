# 数据管理流水线规范 v1

代码是权威，本文只解释 `src/inv_trend/data/pipeline/`。本轮只标准化 K 线（bars）。永续、四资产、成分股和时点行情不迁入这条链路，只按文末方式接入。

`HistoricalDataService` 仍是对外入口。`ingest` / `reprocess_raw` / `load_bars` / `load_bars_version` 委托 `MarketDataPipeline`，方法名、参数和默认值不变。`data.load_bars` 的模块级签名不变。

## 1. 链路与四阶段职责

标准顺序是 `acquire → transform → persist`。`read` 单独进入，不重跑前三阶段。

| 阶段 | 职责 | 实现 |
|---|---|---|
| acquire | 按主源和回退源抓取，并把原始字节与原始帧落盘 | `BarsAcquire` / `BarsCore.fetch` |
| transform | 只做归一化、合并、冲突判定和质量计算，不写盘 | `BarsTransform` / `BarsCore.transform` |
| persist | 只落盘：normalized、quarantine、curated、manifest、catalog | `BarsPersist` / `BarsCore.persist` |
| read | 按版本或当前指针读取，并做可见性过滤 | `BarsRead` / `BarsCore.read` |

`ingest` 就是 acquire、transform、persist 三步。主源没过质量门禁、且品种声明了回退源时，acquire 的 `retry_fallback` 用新的 `run_id` 再走一遍 transform 和 persist。

阶段 2 不调用 `write_normalized`，也不写 quarantine。这两处写盘在阶段 3。Parquet 按内容寻址，写入顺序不改变内容哈希。

## 2. 契约字段

定义在 `pipeline/契约_v1.py`。`PIPELINE_STAGES` 固定为 `("acquire", "transform", "persist", "read")`。

`DatasetKey`：`symbol`、`timeframe`。

`PipelineContext`：`kind`、`key`、`start`、`end`、`run_id`、`retries`（默认 3）。

`AcquireOutcome`：`provider_result`、`raw_path`、`raw_frame_path`、`errors`。另有传递用的 `manifest`，默认为空。

`TransformOutcome`：`normalized`、`clean`、`merged`、`conflicts`、`rejected_incoming`、`quality`、`dataset_version`、`request_id`、`raw_snapshot_id`、`outside_window_revisions`。落盘还要带着 `provider_result`、`raw_path`、`raw_frame_path`、`errors`、`status`、`publishable`、`current_pointer`、`parent_dataset_version`、`is_new_dataset`、`curated_view`、`complete_count`、`inherited_research_only`、`config_hash`、`metadata_hash`。

`PublicationOutcome`：`manifest`、`status`、`publishable`、`dataset_manifest_path`。

端口：

- `DataAcquirePort.acquire(context) -> AcquireOutcome`，并带 `kind`
- `DataTransformPort.transform(acquired, context) -> TransformOutcome`
- `DataPersistPort.persist(transformed, context) -> PublicationOutcome`
- `DataReadPort.read(key, *, version=None, start=None, end=None, adjusted=True, completed_only=True, allow_research=False, allow_legacy=False, min_quality_score=50.0) -> DataFrame`

`PipelineSpec`：`kind`、`acquire`、`transform`、`persist`、`read`、`rule_version`（默认空字符串）。

## 3. 注册表与 kind

`pipeline/注册表_v1.py` 的 `PipelineRegistry` 以 `kind` 保存构造器。

- `register(kind, builder)`：空 kind 或重复 kind 抛出 `ValueError`
- `resolve(kind)`：未注册抛出 `KeyError`
- `kinds()`：返回已排序的 kind 元组

模块函数 `register_pipeline` / `get_pipeline` 使用进程内的默认注册表。内置 `bars` 在导入时注册，构造器是 `build_bars_spec`。

`kind` 用短名字，不用路径。K 线固定为 `"bars"`。新数据集使用自己的名字，例如 `"perpetual"`，不要复用 `"bars"`。

文件名延续 `_v1` 后缀：`契约_v1.py`、`注册表_v1.py`、`流水线_v1.py`、`行情阶段_v1.py`。

## 5. 扩展指引

新增一类同源数据时，只写四个阶段适配器和一次注册。编排、`run_id`、阶段边界、发布和读取入口复用 `MarketDataPipeline`。

```python
from inv_trend.data.pipeline.契约_v1 import (
    AcquireOutcome, DatasetKey, PipelineContext, PipelineSpec,
    PublicationOutcome, TransformOutcome,
)
from inv_trend.data.pipeline.注册表_v1 import register_pipeline
from inv_trend.data.pipeline.流水线_v1 import MarketDataPipeline


class PerpAcquire:
    kind = "perpetual"

    def acquire(self, ctx: PipelineContext) -> AcquireOutcome:
        ...


class PerpTransform:
    def transform(self, acq: AcquireOutcome, ctx: PipelineContext) -> TransformOutcome:
        ...


class PerpPersist:
    def persist(self, tr: TransformOutcome, ctx: PipelineContext) -> PublicationOutcome:
        ...


class PerpRead:
    def read(self, key: DatasetKey, **filters):
        ...


def build_perp_spec(*, instruments, providers, lake, **_ignored) -> PipelineSpec:
    return PipelineSpec(
        kind="perpetual",
        acquire=PerpAcquire(),
        transform=PerpTransform(),
        persist=PerpPersist(),
        read=PerpRead(),
    )


register_pipeline("perpetual", build_perp_spec)
pipeline = MarketDataPipeline.for_kind(
    "perpetual", instruments=instruments, providers=providers, lake=lake,
)
pipeline.ingest(DatasetKey("XYZ", "D1"), start, end)
```

四个适配器只放本数据集特有的获取、转换、保存和读取。不要复制 `MarketDataPipeline.ingest` 的时序。

## 6. 数据后端权威与只读策略

一个数据根只有一个可写权威：`metadata/研究目录_v3.sqlite3`（声明在
`src/inv_trend/infra/backend.py`：`V3_AUTHORITY_PATH`）。两套入口共用同一份声明，
不再各自硬编码路径：

| 入口 | 根的含义 | 权威路径 | 返回对象的 `authority` |
|---|---|---|---|
| `data.open_data_lake(data_root)` | 数据根 | `<data_root>/metadata/研究目录_v3.sqlite3` | `v3` / `legacy` |
| `storage.open_storage(project)` | 项目根 | `<project>/data/metadata/研究目录_v3.sqlite3` | `v3` / `legacy` |

规则：

1. `backend="auto"` 只在权威文件存在时选 v3，否则回落到 legacy；不会静默猜测。
2. 同一根里已有 v3 权威时，`backend="legacy"` 直接失败（`DataLineageError` /
   `StorageIntegrityError`），避免“读 legacy、写 v3”。
3. v3 根里出现 `catalog.sqlite3`、`catalog.duckdb` 或 `catalog_backend.json`
   视为混合布局，`validate_v3_authority` 失败关闭。
4. legacy 目录/结果库处于退役窗口（`infra.backend.LEGACY_STATUS = retirement_window`）：
   只有显式 `backend="legacy"`（测试与历史迁移）才会打开它，日常运行与所有页面读取
   都走 v3 权威；新写入不进入 legacy。
5. 页面与看板只读：`DashboardReader._read()` 以 SQLite `mode=ro` 打开并设置
   `PRAGMA query_only=ON`，`tests/test_监控看板合同.py` 断言该连接拒绝写入且
   看板前后事件库字节一致。写入口只有 CLI/application 用例。
