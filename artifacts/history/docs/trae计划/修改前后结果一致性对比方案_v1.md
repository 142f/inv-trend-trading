# 修改前后结果一致性对比方案 v1

> 目的：对本轮结构重构（P0–P6）做**改前 vs 改后**的产物级一致性对比，证明"对外接口行为与
> 运行结果不变、数值基线完全一致"，并给出可复核的差异证据。
> 范围（已与用户确认）：**离线可复现入口**；判定标准：**规范化后严格相等**。

---

## 1. 摘要

在 `3a09122`（改前）与 `2e89351`（改后）两个 **git worktree** 里，用同一套离线入口产出
同一批产物，剔除契约声明的易变字段后逐字节/逐值比对，输出：

1. 逐文件一致性表（相等数 / 差异数 / 首个差异位置）；
2. 差异分类（数值差异 / 结构差异 / 仅易变字段差异）；
3. 全量回归与 golden master 的双树对比；
4. 反例自检（negative control），证明对比器不是"恒真"。

新增 2 个可复用脚本 + 1 份回执，独立提交。

### 2.3 关键工程约束

1. **venv 指向问题**：`.venv` 中的 `inv_trend` 可能来自 editable 安装并指向主树，
   `pyproject.toml` 的 console scripts（`turtle-data` 等）同样如此。因此两棵树都必须用
   `python -m inv_trend...` + `PYTHONPATH=<tree>/src` 运行，并用守卫断言实际加载路径：
   `python -c "import inv_trend,pathlib; assert pathlib.Path('<tree>') in pathlib.Path(inv_trend.__file__).parents"`。
2. **不得写入被保护目录**：两棵树的 `processed_data/` 与 `outputs/` 均只读；所有产物写入
   `.tmp/compare/{before,after}/...`。`build-metal-tech-core` 只从 `--processed-dir` 读、
   只往 `--output-dir`/`--reports-dir` 写（`ensure_processed_layout` 作用于 `output_dir`）。
3. **易变字段**：产物中含运行时刻与绝对路径（例如 `legacy_report` 写入
   `report_date=今天`、`generated_at=now`；`_build_summary.json` 含绝对路径）。
   必须归一化后再比对，见 §3.4。

## 3. 拟新增的对比设施

### 3.1 `scripts/结构对比_v1.py`（新增，比较器）

职责：给定两个产物根目录，按 §3.4 规则归一化后比对，输出机器可读报告。

- 接口：
  - `--before <dir>` `--after <dir>`（必填）
  - `--out <json>`（默认 `.tmp/compare/对比结果.json`）
  - `--self-test`（反例自检：对 before 树里每个文件依次注入 1 字节差异，断言比较器**能**报出差异；用于证明对比不是恒真）
- 行为：
  1. 递归收集两边相对路径集合：**文件名集合必须相同**，否则报"结构差异"。
  2. 对每个文件按扩展名分派：
     - `.json`：解析 → 递归归一化（§3.4）→ `json.dumps(sort_keys=True)` 的 sha256
     - `.csv`：按行读取 → 路径前缀与时间戳归一化 → 行序不变地比对（并额外做数值列精确相等校验）
     - `.html`/`.txt`：文本归一化 → sha256
     - `.parquet`：`pandas.read_parquet` → dtype/列序/索引**精确相等**断言（`assert_frame_equal(check_exact=True)`）
     - 其它：字节 sha256（仅路径前缀归一化）
  3. 对每个不一致文件输出：首个差异位置（JSON path / 行号 + 列 / 字节偏移）、差异分类标签。
- 退出码：全部相等 → 0；出现非易变字段差异 → 2；仅结构差异 → 3。

### 3.2 `scripts/结构对比_产物_v1.py`（新增，产物生成器）

职责：在**当前所在树**中生成 §2.2 的三类产物，供两棵树各跑一次。

- 接口：`--surface {core-dataset,daily-publish,golden-master,all}` `--out <dir>`（必填）
- `core-dataset`：调用 `inv_trend.cli.data.main` 等价路径（直接调用
  `build_metal_tech_core_dataset(processed_dir=<tree>/processed_data, output_dir=<out>/processed,
  reports_dir=<out>/reports, backtest_config=load_config(None))`），**保留 HTML**（默认）。
- `daily-publish`：构造与 `tests/unit/test_daily_artifact_publication.py` 同形的 snapshot
  （固定 `run_id`/`report_date`），用 `create_daily_run_artifact_writer(<out>/daily,
  signal_log_root=<out>/signals)` + `ArtifactPublicationService(...).publish(snapshot)` 发布，
  随后对发布结果调用 `inv_trend.storage.制品.read_daily(...)` 并把返回值写入
  `<out>/daily_readback.json`（覆盖 P5 删除后的读取路径）。
- `golden-master`：`tests/golden_master_support.build_current_snapshot(load_bars())` →
  写 `<out>/golden_snapshot.json`（含事件/订单/指标；易变字段按 §3.4 归一化）。
- 另写 `<out>/immutable_json_probe.json`：对固定输入调用
  `inv_trend.storage.基础.immutable_json(<out>/probe.json, payload)`，记录返回 sha256 与
  落盘文件 sha256（直接覆盖 P4 的搬动）。
- 输出 `<out>/manifest.json`：`{surface: [相对路径...], python_modules: <len>, tree_commit: <sha>}`。

### 3.3 Golden Master 交叉版本比对

`tests/test_golden_master.py` 只把当前快照与**固定 fixture** 比对；本方案额外用 §3.2 的
`golden-master` surface 把**两棵树各自的快照**互相比对（归一化后），从而把"与 pin 相比
都对"升级为"彼此相同"。

### 3.4 归一化规则（契约化的易变字段白名单）

按顺序施加（全部为**替换为固定 token**，不删除结构）：

| 规则 | 目标 | token |
|---|---|---|
| N1 | worktree 绝对路径前缀（`<tree>` / `<out>` / `<rep>`） | `«ROOT»` / `«OUT»` / `«REP»` |
| N2 | RFC3339/ISO 时间戳（含 `T`、时区偏移或 `Z`） | `«TS»` |
| N3 | 裸 ISO 日期（`"YYYY-MM-DD"`） | `«DATE»` |
| N4 | JSON 键名命中易变集合：`generated_at`、`created_at`、`updated_at`、`evaluated_at`、`now`、`timestamp`（仅当值形如 N2/N3） | `«VOLATILE»` |
| N5 | 文件系统绝对路径字符串（`X:\...` / `/...`，非项目根亦可） | `«PATH»` |
| N6 | `<out>` 目录下的自增/随机目录名或文件名（如 `artifacts/<uuid>`；本次 harness 固定 run_id，预期不触发） | `«ID»` |

**不做归一化**的字段（出现差异即真实差异）：所有数值指标、`decision_id`/`input_key`/
`result_hash` 等内容寻址哈希、事件/订单/交易记录、列序、dtype、行数与行序。

## 5. 假设与决策（执行者无需再选择）

| # | 决策 | 理由 |
|---|---|---|
| D1 | 用 `git worktree` 建改前树，而不是 `git stash`/切分支 | 不干扰主树与用户未提交工作；两树可并存运行 |
| D2 | 两棵树都显式 `PYTHONPATH=<tree>/src` 且用 `python -m`（不用 console script） | `.venv` 的 editable 安装与 `turtle-*` 入口指向主树，否则两树会加载同一份代码，对比失去意义；并有 §2.3-1 的守卫断言 |
| D3 | 同步用户未提交内容进改前树 | 否则差异无法归因于本轮重构；同步后两树唯一差异就是 P0–P6 |
| D4 | **不纳入** `research-stages verify` | ①它可能向 `data/metadata/研究目录_v3.sqlite3` 写回执，有污染受保护数据风险；②该链路的代码（`多方法研究_v1`、`storage.阶段运行_v1`/`研究核验_v1`）本轮未改动；③其覆盖可由现成的 `tests/` 回归补足 |
| D5 | 归一化只在 §3.4 白名单内进行；**数值/哈希/事件记录一律不归一化** | 保证"规范化后严格相等"的判定仍然是强判定，不会被归一化掩盖真实差异 |
| D6 | 保留 HTML 产物参与对比（不做 `--no-html`） | HTML 是 `legacy_report`/`complete_renderer` 的真实产物路径，覆盖面更大；其时间戳由 N2/N3 归一化 |
| D7 | 新增 2 个脚本而非一次性临时脚本 | 便于复跑与复核；`结构对比_v1.py` 的 `--self-test` 使对比器可自证有效 |
| D8 | 不修改任何产品代码；本方案只新增脚本、文档与 `.tmp` 对比产物 | 与"改动最小化"约束一致；若对比发现真实差异，另行单独立项修复 |
| D9 | 对比结果与 junit 落在 `.tmp/compare/`，不进入受保护目录，不入库 | 与既有验收做法一致（`.tmp` 为测试/对比工作区） |

## 6. 验证步骤（含 review×3）

1. **三门禁**：`结构对比_v1.py --self-test` 必须证明能检出差异；`--before/--after` 正式比对
   必须 `exit 0`（全部规范化后相等）；两份 junit 的失败集合必须完全相同。
2. **review 第 1 次（等价性口径）**：核对 §3.4 归一化白名单是否**只**覆盖契约声明的易变字段
   （逐条给出产物中的实例位置），确认没有任何数值/哈希字段被归一化。
3. **review 第 2 次（覆盖面口径）**：用 `git diff --name-only 3a09122..2e89351` 列出重构改动
   文件，逐一映射到 §2.2 的 surface，确认**零遗漏**（含新增 `inv_trend/ports/`、删除的
   `observability/report_model.py`、`observability/backtest_html.py`、`storage/制品.py`
   中被删的两个函数在读取侧的覆盖）。
4. **review 第 3 次（反向/对抗口径）**：主动构造两个反例并确认被检出——
   (a) 篡改一个数值指标；(b) 只改 `generated_at`（应被判定为"仅易变字段差异"并说明）。
5. **交付物**：`docs/修改前后一致性对比_20261020.json`，含每个 surface 的文件数/相等数/差异数、
   首个差异证据（若仅易变字段，则给出"归一化后即相等"的证明）、junit 对比、self-test 结论、
   以及改动文件→surface 的覆盖映射表。
