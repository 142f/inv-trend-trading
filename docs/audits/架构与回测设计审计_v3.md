> 审计日期：2026-08-31  
> 审计对象：当前工作区 `src/inv_trend/`、配置、测试、研究入口与制品契约

## 1. 执行摘要

当前项目已经完成统一包名、Daily 六阶段工作流和统一回测 v2 的主体迁移。附件中的
若干高层方向仍有参考价值，但它描述的是更早的过渡状态，不能作为当前整改清单直接执行。

本轮结论如下：

- `DailyWorkflow` 已是 `turtle-daily` 的规范入口；`DailyMarketScanService` 的 `run()`
  反向委托给工作流，属于仍受测试保护的兼容构造面，不是第二条独立生产流程。
- `inv_trend.application.backtest` 已是规范回测应用入口；`strategy-backtest` 是规范 CLI，
  `turtle-backtest`、`BacktestService` 和 `StrategyBacktestService` 是显式弃用别名。
- 手续费与滑点已经在每次成交时扣减，并进入交易成本和净损益；附件所称“引擎未显式扣减”
  不成立。不过，当前滑点被建模为现金成本而不是成交价偏移，仍是一项模型简化。
- 回测已具备不可变数据来源、参数计划 v2、因果指标、下一根 K 线开盘成交、风险二次校验、
  滚动验证、最终留出集、确定性执行哈希和服务端报告模型，整体研究证据链完整。
- 当前最高优先级风险不是目录归属，而是三项可观察行为：Windows 长路径导致制品发布失败；
  滚动窗口端点的未平仓语义不完整；异步多资产日历下开盘风险预算可能漏计没有当日 K 线的持仓。
- `TurtleBacktester` 仍以约 790 行同时承担时间推进、撮合、风险、账本、成本与估值，适合按
  行为等价方式拆分，但不应先移动目录再补测试。

## 4. 当前架构审计

### 4.1 实际依赖与权威边界

```text
cli ───────────────> application ───────> core
 │                         │               ▲
 │                         ├─────────────> data
 │                         └─────────────> adapters ───> core / data
 └──────────────> observability ────────> core

integrations ───────────────────────────> adapters（AssetSpec 过渡依赖）
```

当前边界与 [`ARCHITECTURE.md`](../ARCHITECTURE.md) 一致：Core 无 IO；Data 不依赖策略或
Application；Application 不依赖 CLI 或表现层。架构测试通过 AST 检查静态和字面量动态导入，
能阻止最危险的反向依赖。

仍有三个约束空白：

1. 没有自动限制 CLI 直接组合 Adapter 或 Data 的范围；`turtle-alert` 是已知例外。
2. 没有自动证明 Observability 不计算业务指标，当前主要依靠代码评审与回测 HTML 测试。
3. Adapter 是过渡边界，尚无按子包声明的允许依赖矩阵，因此职责继续增长不会触发门禁。

建议扩展架构测试时使用明确 allowlist，不采用“所有 Adapter 必须立刻变薄”的一次性规则。

### 4.2 Daily 六阶段工作流

规范流程为：

```text
数据更新 → 策略筛选 → 趋势决策 → 信号提交 → 成果发布 → 通知投递
```

`DailyWorkflow` 通过 `DailyWorkflowRuntimePort` 协调阶段，CLI 对独立阶段分别使用只读、提交、
发布和投递 Adapter。阶段身份、输入 hash、结果 hash、不可变 canonical JSON、事务性
signal/cursor/outbox 提交和恢复行为均有测试覆盖。

`DailyMarketScanService` 仍包含约 660 行历史能力，`LegacyDailyRuntimeAdapter` 约 477 行；
它们的存在增加理解成本，但删除前必须先迁移公开构造者和研究调用面。当前应将它们定义为
“兼容组合层”，禁止新增业务规则，而不是视为第二套工作流继续演进。

### 4.3 配置权威

`src/inv_trend/config/strategy.yaml` 是策略真源；`load_strategy_mapping()` 读取版本化 mapping，
再由 `canonical_to_application_mapping()`、`canonical_to_detector_mapping()` 和
`canonical_to_backtest_mapping()` 映射到各消费者模型。`assets.yaml` 独立拥有市场身份和数据语义。

风险不在“多个 YAML 同时生效”，而在映射层仍带有 legacy shape 和隐式默认值兼容逻辑。
后续应对“规范字段 → 消费者字段 → 序列化 manifest”建立矩阵测试，确保增加规范字段不会无意
改变旧运行指纹。

### 4.4 规模热点与职责

当前源码约 187 个 Python 文件、33,693 行。值得优先控制的热点不是单纯行数，而是状态与 IO
耦合：

| 模块 | 约行数 | 主要风险 |
|---|---:|---|
| `data/api.py` | 1,297 | 用例、质量门控、发布路径集中 |
| `adapters/daily/artifact_publisher.py` | 1,172 | 原子发布、别名、恢复、HTML 和路径策略集中 |
| `application/daily/workflow.py` | 994 | 六阶段协议、恢复和身份校验集中 |
| `adapters/multi_asset/backtest/runner.py` | 790 | 时间推进、撮合、风险、成本、账本和估值集中 |
| `application/backtest/service.py` | 548 | 批次执行、fold 聚合、排名、稳定区间和结论集中 |

拆分标准应是可单独验证的状态转换，不是固定行数阈值。

## 5. 回测设计审计

### 5.1 数据血缘与可复现性

`BacktestSourceBundle` 固定 source run、strategy version、instrument、dataset version 及各阶段
结果 hash；计划、source 和实际 data 的 symbol 集必须完全一致。参数网格先验证、规范化、去重，
并受 `max_combinations` 限制。参数研究不会回写正式策略配置或 Daily 结论。

`BacktestCombinationResult.execution_result_hash` 只覆盖规范化订单、交易和权益曲线，排除操作性
`intent_id`；批次结果 hash 还排除 run id、报告日期和生成时间。整理前基线位于
[`回测整理前基线_v1.json`](../../tests/fixtures/回测整理前基线_v1.json)，当前联合执行 hash 为
`daf2e7da76e19bcb93e98ad48f99ede277e4e7dc91bd0212017f659d5813d26e`。

该设计足以验证重构等价性，但 hash 相等只证明序列化执行事实相等，不证明市场模型真实或统计
选择无偏。

### 5.2 指标与信号因果性

Donchian 通道使用 `rolling(N).max/min().shift(1)`；当前完整 bar 收盘确认信号，下一根有行情的
bar 开盘尝试成交。Wilder ATR、MACD 和 Daily 多周期聚合语义已在
[`ALGORITHM_SEMANTICS.md`](../ALGORITHM_SEMANTICS.md) 固化，并有黄金主测试。

`BacktestDataStore` 在全量历史上预计算指标，evaluation window 只限制执行日期。这为窗口首日提供
只含过去数据的指标预热，不构成前视；但“窗口前数据可用于指标、不可带入仓位”是重要实验假设，
必须在结果和报告中显式标注。

### 5.3 单根 K 线事件顺序

底层执行器当前对每个 union-calendar 日期按以下顺序运行：

```text
1. 执行前一收盘后创建的 pending intent（当日 open）
2. 处理当日盘中止损（同一根 K 线 high/low，跳空按 open 处理）
3. 扣除资金费或借券费
4. 若到全数据末端且启用 liquidate_at_end，则按 close 平仓
5. 按 close/最近可用 close 估值并记录权益
6. 使用当前完整收盘快照生成新 intent，等待未来 bar
```

该顺序是因果的，但会产生需要明确测试的行为：新开仓可以在同一根 K 线开盘成交并在盘中止损；
终端 bar 平掉旧仓后仍可能生成永远没有下一根 bar 可成交的 intent；这些 pending intent 当前不进入
最终订单证据。建议终端日禁止生成新 intent，或将其以 `expired/end_of_test` 记录，二者选择前者，
并用执行 hash 版本化这一语义变化。

### 5.4 多资产日历与风险预算

策略快照会保留各品种最近完成的 bar，`tradable_symbols` 只包含当日真正有 bar 且仍有未来 bar 的
品种。订单只会在目标品种有当日开盘价时成交，这是正确的。

但 fill-time 风险重算的 `prices_at_open` 只包含当前 union-calendar 日期有 bar 的品种；
`PortfolioBudgetPolicy._position_usage()` 会跳过没有价格的现有持仓。因此，在跨交易日历组合中，
当新订单成交而另一持仓当日休市时，总风险、方向风险、cluster 风险和杠杆可能被低估。BTC/ETH
连续 D1 组合通常不会触发，但系统自称 multi-asset，不能依赖标的日历偶然一致。

推荐以“当日 open；若无当日 bar，则使用严格早于当日的最近 close”构造完整、带 stale 标记的
因果估值表。所有持仓必须进入预算，缺少任何可用历史价格时应拒绝新风险，而不是忽略该持仓。

### 5.5 成本、现金与持仓模型

- 成交成本为 `abs(qty × price × point_value) × (cost_bps + slippage_bps) / 10000`，每次 entry/add/exit
  从现金扣减；交易表记录 entry、exit 和 total cost，净 PnL 已扣成本。
- 当前 `slippage_bps` 只是现金费用，不改变 fill price、初始止损、加仓锚点或 gross PnL。它等价于
  附加交易费，不是方向相关的真实滑点。建议未来拆成 `commission_bps` 与方向相关成交价滑移；在此
  之前报告必须称其为“成本化滑点”。
- `derivative` 模型只将已实现和未实现 PnL 计入现金/权益；`cash` 模型按买卖名义金额改变现金。
  二者均由同一风险预算限制，不模拟保证金追缴、强平、交易所梯度保证金或订单簿流动性。
- funding 按 `cash -= side × notional × rate` 处理，正 rate 表示多头支付、空头收取；borrow rate 只向
  空头收费。数据列的符号和频率必须由 AssetSpec/数据契约保证，当前引擎不会年化或重采样。

### 5.6 滚动验证、留出集与窗口边界

默认计划采用 1,460 根 expanding train、365 根 validation、365 根步长、365 根最终 holdout，
至少三个 fold。所有组合先按 validation 聚合指标过门槛和排名，第一名再以 holdout 总收益非负确认；
holdout 排名只进入过拟合风险标记，不反向改变 validation 第一名。这一选择顺序基本合理。

当前每个 train、validation、holdout 都重新创建初始现金、空 PortfolioState 和空 ReservationBook；
窗口前历史只用于指标预热。窗口末端的 `liquidate_at_end` 判断却比较品种的全数据最后日期，而不是
evaluation end。因此普通 fold 末端不会强制平仓：权益收益含未实现 PnL，`trade_count`、胜率、盈亏比、
持有期和成本统计却只含已完成交易。这会让同一窗口的权益类指标和交易类门槛使用不同闭合口径。

推荐将该语义版本化为 `window_boundary_policy: mark_to_market`，默认保持窗口起点空仓、终点按市值计价，
同时新增 `open_position_count`、`unrealized_pnl`、`closed_trade_count`，并明确
`ranking.min_oos_trades` 使用 `closed_trade_count`。不要为凑齐交易统计而在每个年末强制虚构平仓。
旧 v2 结果只读；新策略改变 schema 或 assumptions hash，并保留旧执行基线。

### 5.7 绩效、排名与报告

Application 指标对不可定义的 Sharpe、Sortino、MAR、胜率等返回 `null`，原因写入 `unavailable`；
这是正确的报告契约。Core 的轻量 `equity_statistics()` 则将零波动 Sharpe 等返回 0，服务对象不同，
但共享数学口径存在漂移风险。

不建议删除其中一个函数并让所有调用者直接改用另一个。应先提取纯数学 kernel，返回可选值与原因；
Detector 可在边界适配为历史零值，统一回测继续输出 `null + reason`。迁移必须对 CAGR、波动率、
最大回撤和 Sharpe 建立交叉属性测试。

报告 schema 当前为 v1，批次 schema 为 v2，这是两个不同契约，不是版本倒退。服务端负责指标、排名、
热力图、稳定区间和结论；浏览器只展示 JSON。HTML 可重新生成，不应进入执行 hash。

## 7. 兼容入口移除门槛

以下对象当前不得仅因“是 wrapper”而删除：`turtle-backtest`、`BacktestService`、
`StrategyBacktestService`、`inv_trend.application.strategy_backtest`、旧报告写入函数。

每个入口只有同时满足以下条件才可移除：

1. 已记录首次弃用版本和计划移除版本，至少跨一个正式发行版本持续警告；
2. `src`、`tests`、`research`、脚本、README 和操作文档中没有规范外调用；
3. 对外参数、返回对象、输出路径和警告行为有迁移说明；
4. 旧入口与新入口的行为等价测试先通过，再在下一版本删除旧测试；
5. 历史产物索引和 v1/v2 只读报告转换不依赖被删实现；
6. 删除后全量测试、CLI smoke、黄金主和执行 hash 基线全部通过。

当前 `research/d1_suite/scripts/run_d1_multi_asset_equity_overlay.py` 仍导入 `BacktestService`，因此
`BacktestService` 尚未满足第 2 条。

### 8.2 每项回测语义变更的强制证据

1. 保存旧批次结果，禁止覆盖；
2. 对同一 source bundle、计划和数据执行新旧实现；
3. 分别比较 orders、trades、equity 和联合 `execution_result_hash`；
4. 若目标是纯重构，所有执行 hash 必须完全一致；
5. 若目标是修复语义，记录首个差异事件、因果解释、新 schema/assumptions hash 和新基线；
6. 派生浮点指标在声明等价时最大误差不超过 `1e-12`；
7. 报告只能从保存的批次 JSON 再生成，不允许浏览器重算。

## 9. 最终判断

项目当前不是“架构尚未建立”，而是已经进入迁移后半程：规范入口、因果规则、版本化结果和审计
证据链均已具备。下一阶段最有价值的工作不是大规模移动文件，而是让窗口边界、多资产估值和
制品发布在测试中变成不可歧义的不变量，再在这些不变量保护下拆分大型执行器和收尾兼容层。

附件提出的 P0/P1/P2 不能原样执行。尤其是删除 wrapper、把全部 Adapter 上移 Core、机械合并
绩效函数，都会跳过当前仍存在的调用者或消费者语义。应采用本文件第 6 节的优先级，并持续遵守
[`回测模块清理审计_v2.md`](../回测模块清理审计_v2.md) 的历史产物保护和执行 hash 门槛。
